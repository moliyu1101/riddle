# Riddle 断点续挖与漏洞保留自动化升级方案

> 文档定位：面向当前在跑项目（Riddle）的完整分析与自动化改造方案。
> 触发背景：部署重启导致 worker 从 0 重扫并直接判定"无漏洞"，已实证的越权漏洞因未走到 submit_finding 而被丢弃。
> 结论先行：已 submit 的漏洞实时落库、不会丢；唯一真实损失窗口是「已实证但未提交」。本方案用自动化堵住这个窗口，并把断点续挖从「依赖人工摸数据库」改造成能力。

---

## 一、完整分析

### 1.1 事件根因链（本次事故）

1. 部署/重启硬杀 worker 进程。
2. worker 未走到「优雅返回」路径，因此没有触发 orchestrator 的断点写入（_apply_resume_context）。
3. 容器重启后 worker 无检查点可读，从 0 开始泛扫。
4. 扫完后 LLM 直接 finish(verdict=no_vuln)。
5. 之前已实证的越权漏洞（role/set?userId=...&role=admin/sadmin 等）被覆盖判定为"无漏洞"。

表层是「重启丢断点」，但把生命周期看完整后发现：真正的数据流是 evid → finding_submitted 事件 → 落库，中间只有一段「已实证、未调用 submit_finding」的窗口会丢，其余全部在盘上。

### 1.2 现行断点/续挖机制盘点（代码事实）

四个自动续挖/深挖路径全部位于 orchestrator.py / deepen.py，均无需人工干预：

| 路径 | 位置 | 触发方式 | 行为 |
|------|------|----------|------|
| A. LLM 中断回队 | orchestrator.py `_apply_resume_context`(2999-3031) | worker 优雅返回带 resume_context | 把会话态/笔记写进 deepen_context，目标回队续挖 |
| B. worker_lead 自动深挖 | orchestrator.py(2830-2860) | worker 返回 deepen_lead 且没打穿 | 自动带定向指令再派一轮 |
| C. 审核打回深挖 | deepen.py `apply_deepen`(33-76) | ai/user 审核把 finding 打回 | 原 finding 标 superseded，目标带指令回队 |
| D. 检查点硬杀恢复 | worker.py `_restore_interrupt_progress`(953-1010) | 每轮落盘 resume_checkpoint.json，重启优先读 | 硬杀/崩溃/重启也能从最近快照续挖 |

证据层：evidence_trail.py 把每次真实请求/响应增量落盘，与 LLM 完全解耦，已取证的越权漏洞证据永久在盘上。

worker 提交链路：submit_finding(_backfill_finding_fields@2046) → 实时 emit finding_submitted → orchestrator 同步落库。因此已提交即已持久化。

### 1.3 核心缺口（按影响排序）

1. 没有手动重挖入口。tasks.py 只有 skip(1292)/directive 注入(1302, 仅运行中)/start/pause/stop。已终态目标无法一键重新入队续挖，只能改数据库。
2. worker 正常结束会删检查点（worker.py 736-744）。对"已判无漏洞"的目标重挖时无检查点，续挖 worker 从 0 泛扫，丢上一轮取证线索。
3. 手动重挖缺少证据注入。即便回队，若不把 evidence_trail 里同目标最近取证摘要注入 directive，续挖 worker 看不到上一轮在打 role/set 越权。
4. 前端无重挖按钮，只能运维直接摸数据库，不可复用。
5. 自动恢复策略在此前迭代里被整体移除（commit e1c9abc，"LLM 超时自动重建漏洞"被删），因会把任意一次请求硬判为高危越权造成误报。教训：不能无脑重建，但也不应因此彻底放弃自动化留白——应改为"确定性、有据可依"的自动恢复，而非粗暴重判。

## 二、自动化升级方案

### 设计原则

- 不回溯改动运行中的任务；只新增能力。
- 一切恢复/续挖必须"有实据"，只认 evidence_trail 里落盘的证据，杜绝自动造洞。
- 保密的恢复不依赖检查点文件（检查点会被清理），依赖永远在盘上的证据链。
- 对外提供 API + 前端入口，替代改数据库。

### 阶段一：手动重挖后端接口（自动化能力底座）

改动文件:app/orchestrator.py、app/api/tasks.py

1. orchestrator.py 新增 `requeue_target(task_id, target_id, directive)`：
   - 校验目标归属与任务状态；
   - status→queued，清 verdict/heartbeat/dead_reason/assigned_worker；
   - deepen_count 累加，priority_score 抬升 100，写 priority_reason；
   - 不依赖 finding 对象（与 apply_deepen 的区别，因为它要求一个 finding，不适用于"未 submit 就重启"场景）。
2. tasks.py 新增 `POST /{task_id}/targets/{target_id}/requeue`，body 带可选 directive。

可行性依据（已读代码确认）：
- _pop_queued 按 priority_score 降序派发(953-956)，手动回队的目标会排到队首；
- 带 deepen_context 的目标天然豁免簇冷却(1004-1016)与低成功率预筛(1195-1196)，不会被拦截；
- worker 构造时见 deepen_context 即走 _deepen_brief 续挖分支(worker.py 370-372,1046-1089)，不会泛扫。

### 阶段二：重挖自动注入证据链（堵住真正的丢失窗口）

改动文件:app/orchestrator.py（或抽独立函数）

1. requeue_target 写 deepen_context 时，若该目标 work_dir 存在 evidence_trail.jsonl，抽取最近 N 条取证动作，拼进 directive。
2. 置 source="user_requeue"，worker 首轮即带证据验证同一个点。
3. 抽取逻辑复用 worker._recent_evidence_brief 的思路，抽成证据模块内独立函数，供 worker 与 requeue 共用，避免逻辑漂移。

效果：重挖不依赖检查点，依赖永远在的证据链，彻底绕过「正常结束删检查点」的坑。

### 阶段三：自动认领「已实证未提交」的漏洞（核心自动化兜底）

改动文件:app/agents/worker.py、可用 addon 注入

1. worker 每轮调用证据链后维护内存内的 `_pending_evidence`（已实证、尚未 submit 的高价值动作）。
2. worker 主循环里，若连续 N 轮无新工具调用（将收尾/被打断前），触发确定性兜底：从 _pending_evidence 生成暂存 Finding 并 emit `finding_pending` 交给 orchestrator 暂存（不判定、不造洞，仅留证据与判词）。
3. 这些暂存 finding 不会进入统一查重/不会被真正 submit（不污染终态），只作为「断点续挖的输入」，下一轮续挖 worker 读盘续挖时自动认领。
4. 明确不做：不把任意一次请求硬判为高危越权（吸收 e1c9abc 教训），只做「有实据的进度留存」。判定权始终留给续挖 LLM。

### 阶段四：前端一键重挖

改动文件:web 前端（目标列表/看板）

对已终态目标加"重新挖掘"按钮，弹出 directive 输入框（可留空，默认"继续验证上一轮取证的漏洞，提交完整利用链+请求响应证据"）。
复用现有 skip/list 的路由与前端模式，改动小。全程需鉴权，接入 RIDDLE_API_TOKEN。

### 阶段五：检查点生命周期收紧（可选，最后做）

把「正常结束删检查点」改为「保留最近一份并标注 finished」，或加开关。收益有限、风险中等，不作为本次必需。

## 三、自动化边界与红线

- 恢复只认盘上证据（evidence_trail），绝不凭 LLM 一句话造洞。
- 暂存 finding 不参与查重、不自动 submit，仅作为续挖输入；判定权始终在 LLM。
- 手动重挖 API 与前端入口必须走鉴权。
- 不回溯改动运行中的任务与已提交漏洞。

---

## 四、验收标准

1. 阶段一：调用 requeue 接口后，目标回到 queued 且排到队首；worker 启动事件 mode=deepen（非自由挖掘）。
2. 阶段二：重挖 worker 轨迹（trace, 1311-1357）首轮即出现 role/set 越权验证请求并附完整响应，而非重新全站枚举。
3. 阶段三：worker 被打断/收尾前若无新动作，自动 emit finding_pending 暂存；续挖时自动认领同一目标证据。
4. 端到端：对 api1-softtone-cn.vpn.cumtb.edu.cn 重挖，续挖 worker 直接认领之前 28 条 role/set 越权证据并正式 submit，不再判定无漏洞。

---

## 五、实施建议步骤

1. 先落阶段一+阶段二（解决本次刚需，且逻辑最小、风险最低），单测+本地回归通过后再部署。
2. 阶段三作为自动化兜底核心，与阶段一/二共用证据抽取函数，代码量可控。
3. 阶段四前端与阶段三并行，阶段五按需。
4. 每次部署走现有流程：git pull → docker compose build → 重启 → 健康检查。
